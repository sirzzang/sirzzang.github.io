    워크플로 해부: GitLab CI에서 Gitea Actions로

    책 3.4.1절의 CI 워크플로에 대응하는 실습이다. 책의 GitLab CI 구성을 Gitea Actions로 옮겼다. 3.4.1편에서 설치한 러너가 잡을 받아 DinD(Docker-in-Docker)의 컨테이너에서 실행한다.

    지속 통합(Continuous Integration, CI)은 코드 변경을 합칠 때 빌드와 테스트를 자동으로 실행하는 과정이다. 이번 워크플로는 테스트를 통과한 코드로 이미지를 만들고, 배포할 이미지 태그까지 Git에 반영한다. 파일 위치는 ~/ml-study/chapters/app-ci/.gitea/workflows/ci.yaml이다. ~/ml-study는 실습 저장소 경로를 줄인 표기이며, app-ci는 Gitea로 push하는 별도 Git 저장소다.

    책의 GitLab CI Gitea Actions에서 사용한 구성
    stages: [test, build, update] 세 jobs와 needs 의존 관계
    잡의 image와 services: dind runs-on: ubuntu-latest 라벨에 연결된 잡 이미지와 러너의 dind
    CI_PROJECT_DIR checkout한 작업 디렉터리인 github.workspace
    CI_COMMIT_SHA 셸 환경 변수 GITHUB_SHA
    CI_COMMIT_SHA 앞 8자리 cut -c1-8로 계산한 SHORT_SHA
    차트 수정 후 액세스 토큰으로 push checkout이 설정한 자동 토큰 인증으로 push

    잡(job)은 여러 단계(step)를 순서대로 실행하는 단위다. needs는 앞 잡의 성공을 다음 잡의 실행 조건으로 만든다. 잡마다 작업 공간을 새로 준비하므로 세 잡 모두 checkout한다.

    flowchart LR
    P[main에 코드 push] --> T[test_code<br/>pytest]
    T --> B[build_image<br/>docker build / push]
    B --> R[Docker Hub<br/>커밋 앞 8자리 태그]
    B --> U[update_helm_chart<br/>yq로 image.tag 수정]
    U --> G[Gitea main<br/>skip ci 커밋]
    G --> A[Argo CD 동기화]
    AI를 이용해 직접 그린 도식. 세 CI 잡의 의존 관계와 이미지·차트 변경의 전달 경로

    on.push.branches: [main]은 실행 대상 브랜치를 고른다. 차트를 갱신하는 잡도 main에 push하므로, 이 필터만으로 재실행을 막을 수는 없다. 차트 커밋에는 실행을 건너뛰도록 [skip ci]를 넣었다. Gitea v1.27에는 Actions 자동 토큰 사용자가 만든 이벤트의 재귀 실행을 막는 처리도 있다(Gitea v1.27 소스).

    변수와 시크릿

    저장소의 Settings → Actions에는 Variables와 Secrets가 따로 있다. 컨텍스트(context)는 워크플로 식에서 값을 조회하는 이름 공간이다. Variables는 vars, Secrets는 secrets로 읽는다.

    이름 용도 run #2에서 읽은 위치
    DOCKER_USERNAME Docker Hub 이미지의 계정명 Secrets. Variables를 먼저 조회하고 비어 있으면 Secrets 사용
    DOCKER_PASSWORD Docker Hub push 인증 Secrets의 개인 액세스 토큰
    MY_ACCESS_TOKEN 별도로 생성한 Gitea 액세스 토큰 이 워크플로에서는 참조하지 않음

    일반 변수는 로그에 표시되고, 시크릿 값은 러너가 ***로 가린다. 변수 이름에는 GITEA_·GITHUB_ 예약 접두사를 쓸 수 없다(Gitea 변수 문서). Docker Hub 토큰에는 이미지를 올릴 쓰기 권한이 필요하다. docker login --password-stdin은 토큰을 표준 입력으로 받아 인증한다(Docker 로그인 문서).

    직접 캡처. Docker Hub에서 개인 액세스 토큰을 Repo Read & Write 권한으로 만드는 화면

    계정명을 Variables에 두면 로그에서 이미지 이름을 확인하기 편하다. 이번 성공 실행은 Secrets에 둔 값을 폴백으로 읽었으며, Variables로 옮긴 뒤의 실행은 시험하지 않았다.

    자동 토큰과 액세스 토큰

    자동 토큰은 Gitea가 Actions 잡에 발급하는 인증 수단이다. 사용자가 직접 만들어 등록하는 개인 액세스 토큰(Personal Access Token, PAT)과 발급·관리 방식이 다르다. 책의 GitLab 예제는 별도 액세스 토큰으로 차트 변경을 push하지만, 이 워크플로는 actions/checkout@v4가 기본 토큰으로 구성한 Git 인증을 사용한다.

    Gitea 1.27의 토큰 권한 문서는 잡 단위 permissions와 contents 범위를 지원한다고 설명한다. contents: write는 코드·릴리스 쓰기 권한 요청이며, 실제 권한에는 저장소·소유자 설정의 상한도 적용된다. run #2에서는 이 설정으로 같은 저장소에 push했다.

    세 잡의 실행 내용

    테스트 잡은 actions/setup-python@v5로 Python 3.10을 준비하고 requirements.txt를 설치한 뒤 pytest를 실행한다. pytest는 파이썬 테스트 실행 도구다. 3.2.1편의 앱에 들어 있는 HTTP 테스트 한 개가 대상이다.

    실습 의존성에는 httpx==0.27.2가 들어 있다. 오래된 Starlette의 TestClient는 httpx에 app 인자를 넘기는데, httpx 0.28은 이 인자를 제거했다. Starlette에서는 0.37.2에 해당 호출을 고쳤다(httpx 0.28 릴리스, Starlette 릴리스 노트). 이 조합으로 run #1의 테스트가 통과했고, app 인자의 폐기 예정 경고 한 건이 남았다.

    빌드 잡은 소스 커밋 앞 8자리로 태그를 만든다. 차트 갱신 잡은 YAML 편집 도구인 yq로 hello-joker/values.yaml의 image.tag를 바꾼다. 따라서 앱 코드 커밋과 차트 수정 커밋의 해시는 달라진다. 이미지 태그는 앱 코드를 빌드한 커밋을 가리킨다.

    run #2의 ci.yaml 
    # .gitea/workflows/ci.yaml: 테스트 → 이미지 push → 차트 갱신
name: ci
on:
  push:
    branches: [main]
jobs:
  test_code:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.10"
      - name: Test
        run: |
          pip install -r "${{ github.workspace }}/requirements.txt"
          pytest "${{ github.workspace }}/"
  build_image:
    needs: test_code
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build and push image
        env:
          DOCKER_USERNAME: ${{ vars.DOCKER_USERNAME || secrets.DOCKER_USERNAME }}
          DOCKER_PASSWORD: ${{ secrets.DOCKER_PASSWORD }}
        run: |
          docker version
          test -n "${DOCKER_USERNAME}" || { echo "::error::DOCKER_USERNAME이 비어 있음. 저장소 Settings → Actions → Variables(또는 Secrets)에 등록"; exit 1; }
          IMAGE="${DOCKER_USERNAME}/hello-joker"
          SHORT_SHA=$(echo "${GITHUB_SHA}" | cut -c1-8)
          docker build . -t "${IMAGE}:${SHORT_SHA}"
          echo "${DOCKER_PASSWORD}" | docker login -u "${DOCKER_USERNAME}" --password-stdin
          docker push "${IMAGE}:${SHORT_SHA}"
  update_helm_chart:
    needs: build_image
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
      - name: Install git and yq
        run: |
          command -v git >/dev/null || (apt-get update && apt-get install -y git)
          mkdir -p "$HOME/.local/bin"
          wget https://github.com/mikefarah/yq/releases/download/v4.2.0/yq_linux_amd64 -O "$HOME/.local/bin/yq"
          chmod +x "$HOME/.local/bin/yq"
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Update helm chart image tag
        run: |
          SHORT_SHA=$(echo "${GITHUB_SHA}" | cut -c1-8)
          git config --global user.email "${GITHUB_ACTOR}@noreply.local"
          git config --global user.name "${GITHUB_ACTOR}"
          yq e -i ".image.tag |= \"${SHORT_SHA}\"" hello-joker/values.yaml
          git add hello-joker/values.yaml
          git commit -m "[skip ci] Update helm chart ${SHORT_SHA}"
          git push origin HEAD:main

    wget은 yq 바이너리를 내려받고, chmod +x는 실행 권한을 붙인다. GITHUB_PATH 파일에 쓴 디렉터리는 다음 step부터 PATH에 추가된다. 여기의 git config --global은 일회성 잡 컨테이너 안의 Git 신원 설정이다.


    적용과 관찰: 첫 실행

    내용을 채운 ci.yaml을 push한 run #1의 커밋은 0d9be20이었다. 러너는 docker.gitea.com/runner-images:ubuntu-latest를 받아 잡 컨테이너와 잡 전용 네트워크를 만들었다. 액션 구현은 GitHub에서, 앱 코드는 Gitea에서 각각 받았다.

    직접 캡처. run #1이 시작된 직후 화면. needs로 이어진 세 잡 중 test_code가 실행 중이다
    # run #1 test_code 로그의 다운로드 경로
https://github.com/actions/checkout
https://github.com/actions/setup-python
From http://gitea-http.gitea.svc.cluster.local:3000/mlops/gitea-ci-example

    checkout은 러너 등록에 사용한 클러스터 내부 주소로 성공했다. Mac LAN IP를 넣은 ROOT_URL과의 구분은 3.4.2편에 있다.

    첫 test_code는 이미지 pull 약 26초를 포함해 44초가 걸렸다. Python 3.10.22에서 테스트 한 개가 통과했지만, 다음 build_image가 이미지 태그 오류로 실패해 update_helm_chart는 건너뛰었다.


    트러블슈팅

    사례 1: 빈 워크플로 파일

    증상: Workflow config file is invalid EOF

    처음 저장소를 push했을 때 Actions 화면에 Workflow config file is invalid. Please check your config file: EOF가 표시됐다. 잡은 시작되지 않았다.

    증거: 첫 커밋의 0바이트 ci.yaml

    Gitea 로그에는 다음 메시지가 있었다. 첫 커밋 c11f2c2에 들어 있는 .gitea/workflows/ci.yaml도 0바이트였다.

    # Gitea가 워크플로를 읽다가 남긴 로그
ignore invalid workflow "ci.yaml": EOF

    원인: 내용 없이 커밋된 파일

    워크플로 파일 경로만 만들어 두고 샘플 내용을 채우기 전에 커밋했다. EOF(End of File)는 읽을 내용 없이 파일 끝에 도달했음을 나타낸다.

    해결: 워크플로 작성 후 재push

    세 잡을 정의한 YAML을 채워 0d9be20으로 push했다. run #1에서 test_code가 실행되면서 워크플로 인식을 확인했다. 이후 push 전에 파일 크기와 커밋 내용을 확인할 수 있다.

    # 워크플로 파일 크기와 실제 커밋 내용을 확인
wc -c .gitea/workflows/ci.yaml
git show HEAD:.gitea/workflows/ci.yaml

    사례 2: 이미지 이름의 계정명 누락

    증상: invalid reference format

    run #1의 Build and push image step은 docker version까지 정상적으로 출력한 뒤 실패했다. Docker 클라이언트는 29.9.2, 서버는 29.5.2였고 둘 다 linux/arm64였다.

    # run #1 build_image 오류
ERROR: failed to build: invalid tag "/hello-joker:0d9be204": invalid reference format

    직접 캡처. run #1의 build_image가 invalid reference format으로 실패하고 update_helm_chart는 건너뛴 화면

    증거: vars 평가 결과와 빈 환경 변수

    잡 로그에서 vars.DOCKER_USERNAME으로 조합한 이미지 이름이 /hello-joker로 평가됐고, step 환경의 DOCKER_USERNAME도 비어 있었다. 저장소 설정에서는 이 이름을 Secrets에 등록한 상태였다.

    직접 캡처. 저장소 Settings → Actions → Secrets에 DOCKER_USERNAME과 DOCKER_PASSWORD가 함께 등록된 화면

    원인: 서로 다른 변수 저장 위치

    vars.DOCKER_USERNAME은 Variables를 조회한다. Secrets에 같은 이름이 있어도 이 조회의 값은 채워지지 않는다. run #1에서는 없는 변수의 조회 결과가 빈 문자열이 되어 Docker까지 전달됐다. 이미지 이름의 계정명 부분이 사라진 이유다.

    해결: 폴백과 빈 값 검사

    커밋 9fc8cad에서 Variables를 먼저 읽고, 비어 있으면 Secrets를 읽도록 바꿨다. ||는 앞 값이 거짓으로 평가되면 뒤 값을 선택하는 식 연산자다(Actions 식 문서).

    # build step의 환경 변수: Variables 우선, 없으면 Secrets
DOCKER_USERNAME: ${{ vars.DOCKER_USERNAME || secrets.DOCKER_USERNAME }}

    전역 env에 있던 IMAGE 조합은 build step의 셸 안으로 옮겼다. 계정명이 비었으면 test -n 검사에서 명시적인 오류를 내고 종료한다. 이 수정 뒤 run #2가 이미지를 정상적으로 push했다.


    검증: run #2

    세 잡의 결과는 test_code 2초, build_image 2분 23초, update_helm_chart 2초로 모두 성공이었다.

    test_code가 run #1의 44초보다 짧았던 데는 두 가지 이유가 있다. 잡 이미지가 이미 dind에 있어 다시 받지 않았다. 또 setup-python이 설치한 Python과 pip 패키지가 run #1의 결과로 남아 있었다. 러너는 잡 컨테이너마다 dind의 act-toolcache 볼륨을 /opt/hostedtoolcache에 연결한다. 작업 공간은 잡마다 새로 준비되지만, 이 도구 캐시는 잡과 실행 사이에 공유된다.

    # run #2 test_code 로그의 pip 출력 발췌
Requirement already satisfied: fastapi==0.95.2 in /opt/hostedtoolcache/Python/3.10.22/arm64/lib/python3.10/site-packages

    # dind의 Docker 볼륨 목록
kubectl -n gitea exec runner-runner-0 -c dind -- docker volume ls

# 실행 결과
# DRIVER    VOLUME NAME
# local     act-toolcache

    직접 캡처. run #2에서 세 잡이 성공했고 build_image의 빌드·push 단계가 완료됐다

    이미지 태그와 플랫폼

    build 로그에서 계정명은 ***로 가려졌고 이미지 태그는 9fc8cad1이었다. Docker Hub에도 같은 태그가 생겼다. 플랫폼은 linux/arm64 하나였으며, 화면의 digest 앞자리 c09f5bf621b8은 로그의 이미지 manifest digest와 일치했다.

    직접 캡처. 9fc8cad1은 linux/arm64이고, 앞선 수동 빌드의 v2는 amd64와 arm64를 포함한다

    로그에는 exporting manifest list와 exporting attestation manifest도 있었다. attestation은 빌드 출처 같은 부가 정보를 담는다. manifest list가 출력됐다는 사실만으로 실행 가능한 CPU 아키텍처가 여러 개라는 뜻은 아니다. 이번에는 Docker Hub의 플랫폼 목록과 이미지 manifest를 함께 확인했다. amd64와 arm64 이미지를 함께 배포하는 빌드는 3.2.2편에서 다룬다.

    # dind의 이미지 저장소 확인
kubectl -n gitea exec runner-runner-0 -c dind -- docker info --format '{{.Driver}} {{json .DriverStatus}}'

# 실행 결과
# overlayfs [["driver-type","io.containerd.snapshotter.v1"]]

    driver-type의 io.containerd.snapshotter.v1은 dind의 Docker가 containerd 이미지 저장소를 사용한다는 뜻이다. 이 저장소는 manifest list와 attestation manifest를 함께 저장한다. 클래식 이미지 저장소에서 두 아키텍처를 --load하지 못했던 3.2.2편의 Mac 환경과는 저장소 종류가 다르다.

    차트 갱신 커밋

    update 잡은 자동 토큰을 이용한 AUTHORIZATION: basic *** 인증으로 checkout하고 같은 내부 주소에 push했다. 로그에 남은 핵심 결과다.

    # run #2 update_helm_chart의 커밋·push 결과
[main 37ae87f] [skip ci] Update helm chart 9fc8cad1
9fc8cad..37ae87f  HEAD -> main
Job succeeded

    arm64 잡 컨테이너에서 다운로드한 yq_linux_amd64도 실행됐다. binfmt_misc는 실행 파일 형식별로 사용할 해석기를 등록하는 리눅스 커널 기능이다. 잡 컨테이너는 kind 노드와 같은 Docker Desktop VM 커널을 사용하며, 노드에서 본 등록 목록에는 x86_64 실행 파일용 처리기가 있었다.

    # kind 노드에서 x86_64 실행 파일 처리기 확인
docker exec ml-study-control-plane sh -c 'head -2 /proc/sys/fs/binfmt_misc/rosetta /proc/sys/fs/binfmt_misc/x86_64'

# 실행 결과
# ==> /proc/sys/fs/binfmt_misc/rosetta <==
# enabled
# interpreter /run/rosetta/rosetta
# ==> /proc/sys/fs/binfmt_misc/x86_64 <==
# enabled
# interpreter /usr/bin/qemu-x86_64

    x86_64 처리기가 등록되지 않은 arm64 환경에서는 amd64 바이너리를 실행할 수 없다.

    CI가 원격 main에 커밋을 하나 추가했으므로 로컬 app-ci는 그만큼 뒤에 남는다. 다음 변경을 올리기 전에 git pull로 차트 갱신 커밋을 가져온다.


    정리

    이번 CI는 테스트 결과, 컨테이너 이미지, 배포할 이미지 태그를 연결했다. ML 플랫폼에서 서비스 코드나 플랫폼 구성 요소를 갱신할 때도 이 세 결과의 연결이 필요하다. 이 실습은 앱 테스트와 이미지 배포 준비까지 다뤘으며, 모델의 품질 평가나 학습 파이프라인 실행은 포함하지 않았다.

    차트 변경을 실제 Kubernetes 배포로 연결하는 과정은 3.4.4편에 이어진다. 코드 커밋과 이미지 태그, 배포 설정 커밋을 각각 추적하면 어느 코드가 배포됐는지 확인할 수 있다.
