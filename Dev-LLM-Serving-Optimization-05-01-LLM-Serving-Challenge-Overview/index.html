    Dev Llm Serving Optimization 05 01 Llm Serving Challenge Overview

    2026년 08월 22일 · 32 분 소요

    • 챕터 5 소개
      • 핵심 내용
        • 지금까지 다룬 일반적인 모델 서빙 개념에서 벗어나, 이 장부터는 LLM 서빙 최적화라는 빠르게 성장하는 분야를 본격적으로 다룹니다.
      • 배경
        • ChatGPT 등장(2022년 말) 이후 LLM이 실무에 널리 쓰이게 됐지만, 모델 크기·연산량·서빙 요구사항이 기존 모델과는 차원이 달라 새로운 도전 과제(vLLM, FlashAttention, MLA 같은 개념)가 쏟아지고 있습니다.
      • 이 장에서 다루는 내용:
        • LLM을 효율적으로 서빙하는 것이 왜 비즈니스 성패에 중요한지
        • GPU 등 최신 AI 가속기의 메모리·연산·인터커넥트 특성
        • LLM 서빙의 주요 병목 지점과 완화 방법
        • 모델 로딩 시의 제약 조건
        • prefill/decode 단계에서의 실행 병목
        • 서빙 단계별로 병목이 달라지는 이유 → 이를 설명하기 위해 GPU arithmetic intensity(연산 강도) 개념 도입
      • 목적:
        • 원리를 모르고 시행착오만 반복하면 최적화가 비효율적이 되기 쉬우므로, 이 장에서 탄탄한 기초를 다져 이후 장들에서 다룰 심화 최적화 기법들을 제대로 이해할 수 있게 준비시키는 것이 목표입니다.
      • 책 원문 번역
        • 지금까지 이 책에서는 모델 서빙의 핵심 개념을 설명하고, 머신러닝 모델을 서빙하기 위한 여러 아키텍처 패턴을 소개했으며, 대규모 배포 시 발생하는 트레이드오프를 분석했습니다. 이쯤 되면 모델 서빙 패러다임에 대해 충분히 이해하셨기를 바랍니다. 이제 우리는 전혀 다른 영역으로 중요한 발걸음을 내딛으려 하고 있기 때문입니다. 이번 장에서는 AI 분야에서 가장 빠르게 성장하는 분야 중 하나인, 서비스 제공을 위한 LLM 최적화에 초점을 맞추겠습니다.
        • 2022년 말 ChatGPT가 등장한 이후, LLM은 챗봇과 코드 생성부터 고급 추론 및 의사결정 시스템에 이르기까지 실제 상황에서 AI가 활용되는 방식을 혁신적으로 바꾸어 놓았습니다. 하지만 그 거대한 크기와 높은 연산 요구, 그리고 독특한 서빙 방식은 기존 모델의 서빙 기법을 훨씬 뛰어넘는 어려움을 야기합니다. 새로운 아이디어부터 널리 채택된 프레임워크에 이르기까지, LLM의 서비스 성능을 더 빠르고 효율적으로 최적화하는 분야는 전례 없는 속도로 발전해 왔습니다. 이 분야에 익숙하지 않은 사람이라면 누구나 쉽게 부담을 느낄 수 있어 막막할 수 있습니다. 예를 들어:
          • 기술 블로그를 읽다 보면 이렇게 궁금할 수 있습니다. “불과 1~2년 만에 인기를 얻고 이미 많은 곳에서 채택된 이 vLLM 프레임워크는 도대체 무엇일까?”
          • 연구 논문을 읽다 보면 “FlashAttention은 어떻게 작동하며, 하드웨어 수준에서 어떻게 최적화해 LLM 추론 속도를 높일 수 있을까?”라는 질문이 떠오를 수 있습니다
          • AI 관련 뉴스를 접하다 보면 MLA라는 새로운 용어를 보게 되고, “DeepSeek V3 모델이 서비스 단계에서 다른 어텐션 메커니즘보다 얼마나 더 효율적으로 작동하나요?”라고 궁금해질 수 있습니다

        • 다음 장들에서 이러한 모든 발전 사항들을 소개해 드리겠습니다. 하지만 각 기법을 다루기 전에, 탄탄한 기초 이해를 먼저 다지고 기본 개념에서 점차 더 복잡한 기법으로 나아가야 합니다. 이 장에서는 이전 장들에서 살펴본 모든 서빙 개념, 원칙, 패러다임과 다음 장들에서 다룰 고급 LLM 최적화 기법들을 연결해 줍니다.

        • 먼저 LLM 서비스 환경을 이해해야 합니다. 왜 중요한지, 하드웨어 요구사항은 무엇인지, 그리고 모델 최적화에 대한 감각을 어떻게 키울 수 있는지 알아야 합니다. 특히, LLM을 효율적으로 서비스하는 것이 애플리케이션과 비즈니스의 성공에 왜 처음부터 중요한지 다룰 것입니다. 다음으로는 LLM 서비스에서 현대 하드웨어가 어떤 역할을 하는지 살펴보겠습니다. GPU 같은 AI 가속기를 통해 메모리 구조, 연산 능력, 그리고 상호 연결 기능을 이해해 보겠습니다. 그다음에 다음 내용을 다룰게요:
          • LLM 서비스에서 주요 병목 현상과 이를 완화하는 방법
          • 서비스를 위해 LLM을 로드할 때의 제약 사항
          • LLM 실행 시, 특히 프리필과 디코딩 단계에서 발생하는 병목 현상
          • 왜 모델 서빙이 여러 단계에서 병목 현상을 겪을 수 있는가
        • 마지막 점을 논의하기 위해, 우리는 산술 강도 arithmetic intensity 라는 새로운 개념을 소개합니다.
        • 이 개념들을 이해하는 것이 중요한데, 기본이 없으면 LLM 서비스 최적화가 지치고 시행착오에 의존하는 일이 될 수 있기 때문입니다. 왜 그런지 모르면서도, 혹은 어떻게 그런지만 알고 지역 최적해에 갇히기 쉽습니다.
        • 이 장을 마치면 LLM 최적화의 세계를 자신 있게 탐험할 수 있는 직관을 갖추게 될 것입니다. 다음 장에서는 이 기초를 바탕으로 성능 향상, 비용 절감, 그리고 애플리케이션이 운영 환경에서 요구하는 워크로드에 맞게 LLM을 효율적으로 배포하는 다양한 기법들을 더 자세히 다룰 것입니다.
    • 핵심 요약 : LLM 추론은 도대체 어디서 병목이 생기는가?
      • LLM serving이 왜 어려운지 하드웨어와 실행 병목 관점에서 설명한다. 핵심 병목은 크게 세 가지
        • 사용자 경험 병목: TTFT와 응답 지연이 커질수록 만족도가 떨어진다.
        • 비용 병목: inference GPU 비용이 빠르게 커지고, 모델 크기와 traffic peak가 비용을 지배한다.
        • 하드웨어 병목: GPU compute, memory bandwidth, interconnect, KV cache memory, model loading 시간이 serving 성능을 제한한다.
      • LLM Serving은 항상 GPU 계산 성능(TFLOPS)이 부족해서 느린 것이 아닙니다.
        • 모델을 올릴 때 → GPU VRAM 용량이 중요
        • Prefill → 입력이 길어지면 Compute-bound가 될 수 있음
        • Decode → 대체로 Memory Bandwidth-bound
        • 긴 Context/동시 사용자 증가 → KV Cache 메모리가 큰 문제
        • Multi-GPU → NVLink/NVSwitch/RDMA 같은 Interconnect도 중요

      • 즉 GPU를 고를 때도 단순히: TFLOPS 높은 GPU = 좋은 LLM GPU 라고 판단하면 안되며, 아래를 함께 봐야 함!

    • 부록 A · GPU 마이크로아키텍처 (SM) — 「그 숫자는 어디서 나왔는가」

      본문 「GPU 연산 속성」은 정밀도별 TFLOPS까지만 보면 GPU 선택 판단이 끝납니다. 이 부록은 그 숫자의 출처와 실현율을 설명합니다 — 1979는 왜 1979인가, 왜 실제로는 그 절반도 안 나오는가, FlashAttention이 말하는 「온칩」이 무엇인가.

        • NVIDIA가 지칭하는 CUDA 코어 = CPU 코어 같은 독립적인 처리 유닛이 아니라, 연산 파이프라인의 한 레인(lane)에 가까움

        • 실제 제어 단위는 그 위의 처리 블록(processing block = partition = SM sub-partition). 위 그림에서 큰 사각형 하나가 처리 블록 하나가 맞으며, 그 안에 L0 명령 캐시 + 워프 스케줄러 + 디스패치 유닛 + 레지스터 파일(16,384 × 32-bit) + 연산 유닛(INT32 16 · FP32 32 · FP64 16 + Tensor Core 1개) + LD/ST 8 · SFU 1이 들어 있음. SM 하나 = 이 블록 4개 → SM당 FP32 CUDA 코어 32 × 4 = 128개, Tensor Core 1 × 4 = 4개

          사각형 하나 안에 들어 있는 것(= 한 블록의 구성)

          층 내용 수량(블록당)
          명령 L0 Instruction Cache 1
          스케줄 Warp Scheduler (32 thread/clk) 1
          발행 Dispatch Unit (32 thread/clk) 1
          상태 Register File 16,384 × 32-bit (= 64KB) 1
          연산 INT32 16 · FP32 32 · FP64 16 + 4세대 Tensor Core TC 1개

          → ×4 하면 SM 하나: FP32 CUDA 코어 128개, Tensor Core 4개, 레지스터 256KB, 워프 스케줄러 4개. H100 SXM은 이 SM이 132개니까 FP32 레인이 총 16,896개인 셈입니다.

        • 워프 스케줄러·디스패치 유닛·레지스터 파일이 블록마다 하나씩이므로, 워프를 발행·실행하는 실제 제어 단위는 SM이 아니라 이 블록 (레지스터 파일도 블록당 64KB, SM 전체로는 256KB)
        • 반대로 사각형 바깥쪽에 있는 것 — 위쪽 L1 Instruction Cache, 아래쪽 Tensor Memory Accelerator · 256 KB L1 Data Cache / Shared Memory · Tex ×4 — 은 4개 블록이 공유하는 SM 단위 자원. FlashAttention 등에서 말하는 “온칩(SRAM)”이 바로 이 256KB L1/shared이며 SM마다 하나씩 있음. 오히려 사각형 밖에 있다는 게 중요한데, 이건 4개 블록이 공유하는 SM 단위 자원이라는 뜻이고, 그래서:
          • 워프를 발행·실행하는 실제 제어/스케줄 단위는 SM이 아니라 이 블록 (워프 하나는 한 블록에 배정되고 다른 블록으로 옮겨가지 않음)
          • 반면 shared memory(온칩 SRAM)는 SM 단위라서, 같은 블록(CUDA 블록)이 shared memory로 협력하는 범위는 SM 전체 → FlashAttention이 말하는 “온칩에 타일을 올린다”가 이 256KB 이야기
        • 즉 이 그림에서 “스케줄 경계 = 사각형, 데이터 공유 경계 = SM 전체” 로 나뉘어 있는 게 핵심임
        • 참고: CUDA 코어 vs 텐서 코어 — 스펙표의 「CUDA Cores」는 무엇을 센 숫자인가
          • CUDA 코어: 스칼라 하나짜리 계산기
            • 1클럭에 a x b + c 하나만 처리함. 값 하나 곱하고 하나 더하고 끝
            • 32개 레인이 각자 자기 원소를 맡아서 동시에 처리하는 SIMT 구조
          • 텐서 코어: 작은 행렬 곱셈기 통째
            • 1개의 명령(mma.sync)으로 행렬 타일 하나를 통째로 곱해서 누적함. 예를 들어, 16x8x8x16 같은 타일을 한 번에 처리함. 내부에 곱셈기가 하드와이어드로 격차처럼 깔려 있어서, 한 명령에 수백 번의 곱셈 누적이 동시에 일어남
          • 숫자로 보면 H100 기준 FP32 CUDA 코어는 약 67 TFLOPS인데, FP16 텐서 코어는 1979 TFLOPS입니다 — 같은 칩 안에서 약 30배 차이
          • 위 주석 그림에서 빨간 사각형(처리 블록) 안의 텐서 코어가 아닌 작은 사각형들, 즉 e 연산 유닛 밴드의 INT32 · FP32 · FP64 레인이 흔히 말하는 CUDA 코어 쪽입니다. 텐서 코어는 같은 밴드 안에 있지만 CUDA 코어가 아닌 별도 유닛입니다.

          • 다만 NVIDIA 스펙시트의 CUDA Cores 숫자는 그 밴드 전체가 아니라 FP32 레인만 센 값입니다.

            | 유닛 (블록당) | SM당 | 스펙시트 「CUDA Cores」에 포함? | | — | — | — | | FP32 32 | 128 | 예 — 이 숫자만 셈 | | INT32 16 | 64 | 아니오 | | FP64 16 | 64 | 아니오 (FP64 코어로 따로 표기) | | Tensor Core 1 | 4 | 아니오 (Tensor Cores로 따로 표기) | | LD/ST 8 · SFU 1 | 32 · 4 | 아니오 |

            • 그래서 H100 SXM의 CUDA 코어 16,896개 = 128 × 132 SM = FP32 레인 수입니다.

          • 표 5-1의 숫자를 분해해 보면 어느 유닛에서 나온 값인지가 드러납니다.

              FP32 (CUDA 코어):   16,896 lane × 2 FLOP(FMA) × ~1.98 GHz  ≈ 67 TFLOPS    ← 표 5-1 FP32 67 ✓
  FP64:                8,448 unit × 2 × ~1.98 GHz             ≈ 34 TFLOPS    ← 표 5-1 FP64 34 ✓
  FP16 (Tensor Core):  528 TC × ~1024 MAC/clk × 2 × clock      ≈ 1979 TFLOPS  ← 표 5-1 FP16 TC 1979 ✓
            • 즉 표 5-1의 두 자릿수(FP32 67 / FP64 34)는 e 밴드의 작은 사각형들에서, 네 자릿수(1979 / 3958)는 전부 텐서 코어에서 나옵니다. 같은 SM 안에서 약 30배 차이 — “작은 사각형 32개 vs 블록 1개”의 차이가 이만큼입니다.
          • 서빙 관점의 함의
            • GEMM(어텐션 · MLP)은 전부 텐서 코어에서 돌아감 → CUDA 코어 수는 LLM 서빙 성능 지표로 거의 쓸모가 없음
            • CUDA 코어(FP32/INT32 레인)가 실제로 담당하는 건 softmax, LayerNorm/RMSNorm, RoPE, element-wise, 샘플링 같은 비-GEMM 연산 → 뒤에서 “element-wise · reduction 연산은 로드하는 데이터 대비 연산량이 적어 산술 강도가 낮다”고 말하는 것이 정확히 이 유닛들의 이야기
            • 그래서 표 5-8의 CUDA Cores 18,176을 보고 L40S를 고르면 안 되고, FP16 Tensor Core 362.05 TFLOPS를 봐야 함

          • FP8은? — 정밀도별로 어느 유닛이 도는가

            | 정밀도 | 도는 유닛 | 표 5-1 값(H100 SXM) | | — | — | — | | FP64 / FP32 | CUDA 코어 (FP64 · FP32 레인) | 34 / 67 | | TF32 · BF16 · FP16 | 텐서 코어 | 989 / 1979 / 1979 | | FP8 | 텐서 코어 전용 (Hopper 4세대에서 신설) | 3958 = FP16의 2배 | | INT8 | 텐서 코어 (CUDA 코어에서는 DP4A로 우회 가능) | 3958 TOPS |

            • FP8은 CUDA 코어에 대응 레인이 없습니다. 텐서 코어 내부 데이터 경로가 8비트를 지원하느냐의 문제라서, 이전 세대(A100 · A10)는 표 5-4에서 FP8 지원이 아예 No입니다.
            • 처리량이 FP16의 정확히 2배(1979 → 3958)인 이유도, 같은 텐서 코어에서 비트 폭을 절반으로 줄여 한 클럭에 2배를 밀어넣기 때문 → FP8은 “새 유닛”이 아니라 “같은 유닛의 저정밀 모드”

      A-2. 유닛은 어떻게 발행되고, 왜 다 동시에 돌지 않는가

      • 스케줄러가 1클럭에 명령어 하나를 골라서 해당 타입의 유닛 묶음으로 보냄. 그래서 INT32/FP32/FP64 등이 “서로 다른 코어”가 아니라, 같은 블록 안의 서로 다른 파이프라인으로 존재함
      • INT8은 INT32 유닛에서 돌지 않는다. 실제로 양자화 모델의 INT8 행렬 연산은 대부분 텐서 코어(초록색 큰 블록)에서 처리함. 오히려 INT8은 텐서 코어에서 FP16 대비 2배의 처리량이 나옴. INT8을 쓴다고 유닛이 노는 게 아니라, 제일 강력한 유닛으로 몰아 주는 셈. CUDA 코어 쪽에서도 DP4A 같은 명령으로 32비트 레인 하나에 INT8 4개를 묶어 처리할 수 있음
        • [x] CUDA 코어, Tensor 코어 어떻게 다른지? → 아래 「참고: CUDA 코어 vs 텐서 코어」 토글
        • [x] FP8은? → 같은 토글의 「정밀도별로 어느 유닛이 도는가」 표
        • [ ] INT8을 쓴다고 유닛이 노는 게 아니라 → 이렇게 설명했던 이유는 뭘까? 논다고 받아들이는 게 일반적이기 때문일까?
      • 유닛별 동작
        • [x] INT32 레인으로 가면 FP64는 못 처리하나?
          • 그렇긴 하나, 시간축을 봐야 함.
          • 워프 스케줄러는 1클럭에 명령어 1개를 하나의 파이프라인으로 발행함.
          • 32스레드 워프를 16개 INT32 유닛에 태우면 2클럭이 걸림 → 발행하고 나면 다음 클럭에 스케줄러는 자유롭다 → 그 사이 스케줄러는 다음 클럭에 다른 파이프라인(FP32, FP64 등)으로 별개의 명령을 발행할 수 있음. 즉 “INT32를 쓰는 동안 FP64는 완전히 막힌다”가 아니라, 클럭 단위로 번갈아 발행된다가 정확한 표현
      • 애초에 모든 유닛을 동시에 쓸 수 없고, 그렇게 설계되었음.
        • 어차피 전력 한계 때문에 모든 유닛을 100% 동시에 가동하는 게 불가능하기도 함
        • 설계 자체도 그러함. “하나의 워크로드가 전부 쓰라”가 아니라, 여러 시장(그래픽/HPC/AI) 등의 워크로드 믹스에 맞춰 다이 면적을 배분한 결과.
          • FP64 유닛은 AI 추론에서는 거의 100% 놂 → 그래서 게이밍 GPU(RTX)에서는 FP64 유닛을 아예 1/64 비율로 깎아 버림
            • H100 같은 데이터센터 칩에 FP64가 실린 건 HPC(기상, 시뮬레이션 등) 목적.
          • 반대로 INT32 유닛은 주소 계산, 루프 카운터, 인덱싱 등에 계속해서 쓰이기 때문에, FP 연산과 동시에 돌아감
          • 이는 GPU 아키텍처 변천사에도 반영되었는데, Turing 이후에는 FP32와 INT32를 분리했다 → 겹쳐 돌리기 위해
            • [x] 왜 겹쳐 돌리는가? — 실제 커널의 명령어 상당수가 계산이 아니라 주소 계산이기 때문
              • Pascal까지: FP32와 INT32가 같은 유닛을 공유했음. a[i] * b[i] 한 줄에서도 인덱스 i를 구하는 INT 연산과 실제 곱셈인 FP32 연산이 같은 자리를 놓고 경쟁 → 주소 계산이 FP32 처리량을 잡아먹음
              • Turing 이후: FP32 32개와 INT32 16개를 별도 파이프라인으로 분리 → 워프 스케줄러가 같은 사이클 창에서 FP32 명령과 INT32 명령을 각각 다른 파이프라인으로 동시에 발행 → 루프 카운터·인덱싱이 실수 연산 성능을 깎지 않음
                • NVIDIA는 Turing 백서에서 실제 셰이더 워크로드에서 FP32 명령 100개당 INT 명령이 평균 약 36개 섞여 나온다고 밝혔습니다. 분리하는 것만으로 이만큼을 공짜로 겹칠 수 있게 된 것
              • 그래서 바로 위 문장(“애초에 모든 유닛을 동시에 쓸 수 없다”)과 모순이 아닙니다. 정확히는 모든 유닛이 동시에 돌지는 못하지만, 겹칠 수 있는 조합은 정해져 있다는 뜻입니다 — FP64는 AI 추론에서 거의 놀고, INT32는 거의 항상 FP32와 함께 돕니다
              • 서빙 관점: 이 겹침이 이득을 주는 구간은 softmax · LayerNorm · RoPE · 샘플링 같은 비-GEMM 연산입니다. GEMM은 텐서 코어에서 돌기 때문에 이 이야기의 바깥에 있습니다

      • [x] A-3. GPU 연산 속성을 볼 때 왜 SM 코어 위주로 이야기하는지?

        원래는 그렇게 이야기하지 않는다. 다만 TFLOPS를 분해하거나 Tensor Core 실현율·온칩 메모리를 설명하려는 순간 SM으로 내려갈 수밖에 없다 정도.

        • 연산 속성을 다룰 때 주요한 기본 축: 정밀도별 TFLOPS + Tensor Core 지원 여부
          • 실제 뒤에서 볼 표 5-1의 연산 속성 특성에서도 (FP64 / FP64 TC / FP32 / TF32 TC / BF16 TC / FP16 TC / FP8 TC / INT8 TC) 축으로 이야기함

          • 다만, 더 자세히 보면 나오는 축

            층위 무엇을 보는가 누가 쓰는가
            제품/스펙 층 정밀도별 TFLOPS, Tensor Core 세대, FP8·FP4 지원 여부 서빙 엔지니어 — GPU 선택, 배치 판단
            마이크로아키텍처 층 SM 수, SM당 CUDA/Tensor Core, L1·shared 크기, GPC/TPC 배치 커널 작성자 — FlashAttention, CUTLASS, 컴파일러
          • 이 책에서 말하는 5장 목적은 워크로드가 compute-bound냐, memory-bound냐 이기 때문에, 그 판정에 필요한 건 루프라인의 y축 상한값 정도. SM이 몇 개인지 등은 419 FLOPS/B라는 교차점 계산에 불필요
          • 그럼에도 SM 그림을 살펴 보는 것이 의미가 있는 이유
            1. TFLOPS의 분해식이 SM: TFLOPS = SM 수 * SM 당 Tensor Core 수 * 코어 당 MAC/clock * 2 * clock
              • H100 SXM = 활성 SM 132개(GH 풀 다이의 경우 144개), SM당 FP32 CUDA 코어 128개 + 4세대 Tensor Core 4개
              • 1979 TFLOPS라는 숫자가 어디서 나왔는지 알고 싶다면, 그 기원은 느림
              • 같은 이유로 H100 NVL의 FLOPS가 SXM보다 낮은 것도, SM으로 설명할 수 있음. 아키텍처가 같은데 값이 다른 건 활성 SM 수와 클럭(출력 한도)이 깎였기 때문 → 가로로 비교하면 NVL이 약간 낮다의 원인
            2. 온칩 메모리 계층이 SM 안에 있음
              • 뒤에 나올 그림 5-12(HBM → L2 → L1/Shared → 레지스터)에서 L1/shared는 SM마다 하나씩 붙어 있는 물건(Hopper는 SM당 256KB급, L2는 다이 전체 공유 50MB).
              • FlashAttention이 “온칩에 담아서 HBM 왕복을 줄인다”고 하는데, 그 때의 온칩이 바로 SM 내부 SRAM이라서, 연산 절을 SM 없이 설명하면 6장에서의 메모리 최적화로 넘어 가는 다리가 끊김
            3. 배치(layout)가 실제로 성능에 드러나는 경우가 있음
              • wave quantization: GEMM 타일 수가 SM 수의 배수가 아니면, 마지막 wave에서 SM 대부분이 놀게 됨. 132 SM에 타일이 133개면, 두 번째 wave가 거의 비어서 실효 성능이 절반으로 떨어짐. 배치 크기·TP 분할이 어중간할 때 나오는 계단 현상
                • [ ] wave? 타일? 이런 건 GPU 구조를 알아야 하는 건지..
              • MIG/MPS: SM과 L2를 물리적으로 쪼개서 나눠 주는 기능이라 파티션 경계가 곧 SM 경계임
              • nvidia-smi utilization의 함정: nvidia-smi가 보고하는 utilization은 “SM이 하나라도 일한 시간의 비율”이라서, decode처럼 memory-bound인 구간에서는 대부분의 SM이 대기 중인데도 100%로 보일 수 있음. SM 개념을 알아야 이 숫자를 믿지 않게 됨
                • [ ] decode 중일 때는 그럼 아주 일부의 SM만 일을 하는 건가?
              • 인터커넥트 절에서 정리한 B200의 「스케줄러 통합 — 하나의 커널이 두 die의 SM에 걸쳐 뿌려져야 한다」도 결국 SM 배치 문제
          • 결과적으로 정리하면,
            • 연산 속성을 “읽는” 기준은 SM이 아니라 정밀도별 TFLOPS임. 실무 판단(어떤 GPU를 사야 할까, FP8을 쓸까 말까 등)은 여기서 끝남
            • SM과 그 배치는 그 숫자의 출처와 실현율을 설명할 때 필요함 → “1979 TFLOPS의 1979는 왜 1979로 도출되었는가”, “왜 실제로는 그 절반도 안 나오는가”에 대한 답

                  • 데이터센터 GPU는 전부 x16 인터페이스로 설계되어 있음

  + NIC (400G IB/RoCE는 x16 필요) × 2~8장

  CPU가 주는 128~160레인을 초과

                  • NUMA: Non-Uniform Memory Access
                    • 각 CPU 소켓이 자기 로컬 메모리 채널과 자기 PCIe 루트 컴플렉스를 갖고, 다른 소켓의 메모리/디바이스에 접근할 때는 소켓 간 링크(Intel UPI, AMD Infinity Fabric)를 한 번 더 건너가야 하는 구조 → 이 홉을 건너면 지연이 늘고 대역폭이 깎임

  CPU1 ── PCIe(CPU1) ┴─ GPU5

      • B-3. 인터커넥트의 이해 — “아주 느린 메모리”
        • 비유: 인터커넥트 = 아주 느린 메모리. 엄밀한 정의가 아니라, 성능을 계산할 때 쓰는 직관입니다.
        • 왜 “메모리”인가: 하는 일이 결국 “다른 GPU의 HBM을 주소로 읽는 것”이기 때문입니다. NVLink는 원격 GPU 메모리에 대한 load/store/atomic을 그대로 노출하고, RDMA는 이름 자체가 Remote Direct Memory Access입니다.
        • 왜 “아주 느린”인가: 대역폭이 HBM 3350 → NVLink 900 → PCIe 128 → 노드 간 50GB/s로 떨어집니다(HBM 대비 1/3.7 → 1/26 → 1/67). 지연은 HBM 수백 ns → NVLink 1~2 µs → InfiniBand 5~10 µs.
        • 왜 치명적인가: decode는 토큰 하나마다 동기화 지점을 64회(32레이어 × 2) 지나갑니다. 동기화 지점은 다른 계산으로 가릴 수 없어서, 링크가 느린 만큼 지연으로 그대로 드러납니다.
        • 비유의 한계: 캐시 계층은 하드웨어가 자동으로 처리하지만, 인터커넥트 계층은 NCCL과 병렬화 전략이 명시적으로 결정합니다. 자동으로 최적화되지 않기 때문에 본문 「6. 실무」가 따로 필요합니다.
        • 단위 주의: NVLink 900과 PCIe 128은 양방향 합계 표기이고, HBM 3350은 메모리 대역폭이라 엄밀한 1:1 비교는 아닙니다.
